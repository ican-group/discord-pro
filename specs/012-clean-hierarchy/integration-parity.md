# Spec 012 — Integration Feature-Parity Matrices

Source: read-only inventory of the code at commit `1c20d2a` (production image
`bitbotpro-api:spec011-f245d7ed3bdb`), 2026-11-18. `S` = `backend/server.py`,
`TG` = `backend/telegram_routes.py`, `ZR` = `backend/zendesk_routes.py`,
`WR` = `backend/webhook_router.py`, `FE` = `frontend/src`.

**Status column:** `PORT` = existing feature, ported to the new architecture ·
`PORT+FIX` = ported and a defect found in the inventory is fixed · `DECIDE` =
existing feature whose future needs an explicit owner decision (§ "Decisions")
· `RETIRE?` = proposed for explicit retirement (never silent) · `NEW` = proposed
improvement, not existing today.

**Production reality today:** the API runs `APP_MODE=api` ⇒ **Discord is
disabled** (`DISCORD_ALLOWED=false`), the Mongo knowledge base is disabled, and
`/chat/send` returns a canned "no knowledge base" text when a bot has no KB and
no API integration (S:3929) — so AI replies are effectively off on every channel.
Discord and Telegram only work through the **V1** path; the V2
`connections`/`connected_accounts` layer is mostly bookkeeping (Discord V2 only
routes when `destination.guild_id` is set, which the UI never sets; Telegram V2
never registers a webhook).

Common test/E2E vocabulary: **unit** = pure/in-process with fakes; **adapter** =
in-process with recorded provider HTTP (MockTransport) / fake gateway;
**E2E** = disposable stack (real MongoDB, API image) and, where stated, a
real provider sandbox (test Discord guild, test Telegram bot, Zendesk sandbox).
